Production-Ready OSINT Service with FastAPI

Architecture guidance for the Web Investigator OSINT component

Executive summary. FastAPI is a strong choice for exposing the current OSINT component through a stable HTTP API. However, FastAPI alone does not make the system production-ready. The most important improvements are durable background job execution, PostgreSQL, security controls, durable evidence storage, and operational monitoring.

1. How FastAPI Works

FastAPI maps HTTP routes to ordinary typed Python functions. For example:

@app.post("/investigations")
def create_investigation(request: InvestigationRequest):
    ...

When a client sends JSON to this route, FastAPI:

  1. Routes the request to the correct Python function.
  2. Validates and converts the request using Pydantic models.
  3. Calls the application's service code.
  4. Serializes the returned value as JSON.
  5. Generates OpenAPI documentation, Swagger UI, and ReDoc automatically.

FastAPI also provides dependency injection for authentication, database sessions, authorization, and shared services. It should be a thin HTTP layer around the existing collectors and orchestrator, rather than a replacement for them.

2. How FastAPI Fits the Current Project

The current implementation is a synchronous service workflow:

Streamlit UI
    |
    v
IntelligenceOrchestrator.run()
    |
    v
Collectors running in parallel threads
    |
    v
Domain checks -> source crawling -> evidence capture -> risk scoring
    |
    v

A recommended production architecture is:

Streamlit / Web UI / API client
              |
              | HTTP
              v
           FastAPI
              |
              | enqueue durable job
              v
      Redis or RabbitMQ queue
              |
              v
        OSINT worker process(es)
              |
              +---------------------+
              v                     v
          PostgreSQL       Evidence/Object Storage

This separates quick HTTP request handling from long-running collection and browser automation.

3. Recommended API Contract

Method and routePurpose
POST /v1/investigationsValidate the target, create a job, enqueue it, and return HTTP 202 Accepted.
GET /v1/investigations/{id}Return job status, timestamps, progress, and failure information.
GET /v1/investigations/{id}/resultsReturn observations, sources, evidence, and risk assessment.
GET /v1/investigations/{id}/reportDownload a generated investigation report.
POST /v1/investigations/{id}/cancelRequest cancellation of queued or running work.
GET /health/liveConfirm that the API process is alive.
GET /health/readyConfirm that required dependencies are available.

The create endpoint should return immediately:

{
  "investigation_id": "OSINT_ABC123",
  "status": "QUEUED"
}

The client can poll the status route or receive progress through server-sent events or WebSockets.

4. Why the Investigation Should Use a Job Worker

The current run() workflow performs network requests, launches concurrent collectors, crawls sources, invokes Playwright, captures evidence, and writes many database records. It can take much longer than a normal HTTP request and should not run directly in the API request process.

FastAPI's in-process background tasks are appropriate for small operations. For this workflow, use a durable task system such as:

  • Celery with Redis or RabbitMQ;
  • Dramatiq with Redis or RabbitMQ; or
  • RQ with Redis for a simpler initial setup.

A durable queue provides retry policies, task persistence, independent worker scaling, and recovery when the API process restarts. Merely converting the current method to async def will not make blocking libraries or browser work faster.

5. Is This a Microservice?

The current application is best described as a modular monolith. The Streamlit UI, orchestration, collectors, and storage use direct Python imports and share the same application runtime and database.

Adding FastAPI does not automatically make it a microservice. A microservice is primarily an independent deployment and ownership boundary, not a framework choice.

The component becomes an OSINT microservice when it is independently deployed and consumed through a stable API or message contract:

Main application ---- HTTP ----> OSINT API
                                  |-- dedicated workers
                                  |-- independent deployment
                                  `-- owned data and storage

DNS, RDAP, search, certificate transparency, and web collectors should remain internal modules initially. Turning every collector into a network service would introduce unnecessary deployment, versioning, monitoring, and failure-handling complexity.

6. Production-Readiness Checklist

  1. Durable job workers: Investigations must survive an API or worker process restart.
  2. PostgreSQL: Replace SQLite before running multiple API and worker processes that write concurrently.
  3. Explicit job lifecycle: Use states such as QUEUED, RUNNING, COMPLETED, PARTIAL, FAILED, and CANCELLED.
  4. Idempotency and retries: Retrying a stage must not duplicate observations or repeat completed expensive work unnecessarily.
  5. SSRF protection: Block loopback, private, link-local, cloud metadata, and internal network destinations; validate redirects and URL schemes.
  6. Authentication and authorization: Use API keys or OAuth/JWT, tenant-aware access checks, and audit logging.
  7. Resource controls: Limit concurrent jobs, redirects, pages, response sizes, downloads, browser time, and requests per user.
  8. Durable evidence storage: Store screenshots and reports in S3-compatible storage or an explicitly mounted persistent volume.
  9. Headless browser workers: Production server and container environments should run Playwright headlessly.
  10. Observability: Add structured logs with investigation IDs, metrics, tracing, health checks, and exception reporting.
  11. Database migrations: Replace runtime schema alterations with versioned migrations such as Alembic.
  12. Failure-path testing: Test authorization, validation, timeouts, queue failure, retries, cancellation, partial completion, and database concurrency.

7. Recommended Implementation Direction

Keep the collectors and orchestrator together as one independently deployable OSINT service. Add a thin FastAPI layer, execute investigations in dedicated worker processes, migrate persistence to PostgreSQL, and store evidence in durable object storage. This creates a clean production architecture without prematurely splitting the codebase into many small services.
