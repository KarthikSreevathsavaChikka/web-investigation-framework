Framework Core Implementation Report

Web Investigation Framework — first implementation milestone

Outcome. A clean baseline of the original Web Investigator application was established in the new repository, and the first reusable framework layer was added on a dedicated feature branch. Existing OSINT and Dynamic Web Investigation behavior was preserved.

2. Baseline Import

The current application source, tests, safe configuration templates, and architecture documents were copied into the new repository. The following local or sensitive artifacts were deliberately excluded:

  • Old Git history and metadata
  • Virtual environments and Python caches
  • .env and Streamlit secrets
  • SQLite database files
  • Generated evidence and screenshots
  • Browser profiles and runtime downloads
  • Archives and LibreOffice lock files

The new repository's .gitignore was strengthened to prevent these artifacts from being committed later.

3. New Framework Package

A new UI-independent Python package was created:

This package does not depend on Streamlit or FastAPI. It can be reused by the Streamlit application, future APIs, background workers, a CLI, or automated tests.

4. Models and Lifecycle Statuses

investigator/core/models.py introduces standardized framework models:

  • InvestigationCase: top-level case identity, target, lifecycle, selected modules, timestamps, and metadata.
  • InvestigationTarget: normalized representation of a domain, URL, brand, or other target with confidence and metadata.
  • Evidence: common evidence representation with type, source, value, confidence, and metadata.
  • Finding: standardized analytical finding with severity, confidence, and related evidence identifiers.
  • StageResult: standardized output returned by every pipeline stage.

Validation was added for empty targets, invalid confidence values, inconsistent timestamps, and failed results without an error description.

5. Shared Investigation Context

investigator/core/context.py introduces InvestigationContext, the shared mutable state passed between pipeline stages. It contains:

  • The top-level investigation case
  • Resolved and selected targets
  • Collected evidence
  • Analytical findings
  • Results indexed by stage name
  • Pipeline metadata
  • A thread-safe cancellation signal

Recording a stage result automatically adds its evidence and findings to the shared context.

6. Standard Stage Contract

investigator/core/stage.py defines the abstract InvestigationStage contract. Every future OSINT, Dynamic Web, correlation, risk, or reporting stage will provide:

  • A unique stage name
  • Optional dependencies on earlier stages
  • An optional enable/disable decision
  • An execute(context) method returning StageResult

The file also defines StageProgress and a progress-callback contract for APIs, workers, and user interfaces.

7. Pipeline Engine

investigator/core/pipeline.py adds a deterministic sequential pipeline engine with:

  • Unique stage-name validation
  • Dependency ordering validation
  • Ordered execution
  • Optional and skipped stages
  • Progress-start and progress-completion events
  • Exception conversion into standardized failed results
  • Stop-on-failure behavior
  • Cancellation handling
  • WAITING_FOR_INPUT pause handling
  • Resume support for already completed stages
  • Final case-status and completion-time updates

The pause state is intended for future analyst approval and manual browser authentication workflows.

8. Framework Exceptions

investigator/core/exceptions.py adds a small exception hierarchy:

  • InvestigationFrameworkError
  • PipelineConfigurationError
  • PipelineExecutionError

This distinguishes invalid pipeline definitions and execution-state problems from collector or browser errors.

9. Tests Added

tests/test_framework_core.py adds nine tests covering:

  1. Case creation and target normalization
  2. Target-confidence validation
  3. Failed-result validation
  4. Ordered stage execution and evidence collection
  5. Duplicate and invalid dependency rejection
  6. Exception conversion and pipeline failure
  7. Waiting-for-input pipeline pause
  8. Disabled-stage skipping
  9. Progress callback delivery
Verification result: 57 tests passed — 9 new framework tests and all 48 existing baseline tests. The new framework package also passed Python bytecode compilation checks.

10. Existing Behavior Preserved

This milestone intentionally did not connect the existing application to the new pipeline. The following code remains operational and unchanged by the framework foundation:

  • Streamlit application and current workspace selection
  • OSINT orchestrator and collectors
  • Dynamic Playwright investigation engine
  • Current SQLite repository implementations
  • Existing dashboards and reports

This avoids a high-risk rewrite and provides a stable framework contract before adapting working components.

12. Recommended Next Milestone

The next step should be an OSINT adapter stage, not a rewrite. It should wrap the existing IntelligenceOrchestrator behind the new InvestigationStage contract and map its output into framework evidence and findings.

After the OSINT adapter is stable, create a Dynamic Web adapter for the existing Playwright engine. Only then should the unified pipeline be exposed through FastAPI and background workers.
