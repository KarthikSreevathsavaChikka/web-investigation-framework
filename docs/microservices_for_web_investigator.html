Microservices for the Web Investigator Project

What a microservice means in this project, how it helps, and when to adopt it

Definition. In this project, a microservice means turning one investigation capability into an independently running application with its own API, processing logic, deployment lifecycle, and data ownership. FastAPI can expose the service, but using FastAPI alone does not automatically make a component a microservice.

1. Current Architecture

The project currently behaves mostly as one application:

5. What Makes Them Real Microservices?

The components become microservices when each one has:

  • A stable and versioned API contract
  • Its own running process
  • Independent deployment and scaling
  • A clear, focused responsibility
  • Ownership of its own data
  • Failure isolation
  • No direct Python imports across service boundaries

If both route groups are placed in one FastAPI process and deployed together, that is a structured API or modular monolith—not necessarily two microservices.

6. How Microservices Help This Project

6.1 Independent scaling

OSINT work is primarily network-bound, while Chromium browser investigations consume substantially more memory and CPU. The system could run two OSINT workers and eight browser workers without duplicating the whole UI.

6.2 Browser security isolation

The Dynamic component opens untrusted websites and executes their JavaScript. Separate containers allow dedicated CPU and memory limits, restricted networking, non-root execution, temporary filesystems, and short-lived browser sessions.

6.3 Failure isolation

If Chromium crashes, the Dynamic service may be temporarily affected while the OSINT service and UI remain available.

6.4 Independent deployment

OSINT collectors can be updated without redeploying browser workers, and Playwright can be upgraded independently of the OSINT service.

6.5 One UI for all capabilities

The analyst still sees one product with New Investigation, OSINT Results, Dynamic Analysis, Evidence, and Final Report. The microservice split remains an internal implementation detail.

6.6 Reusable APIs

Streamlit, a case-management system, or a command-line client could use the same authorized OSINT and Dynamic APIs.

Services should exchange data through APIs or events rather than modifying each other's database tables.

9. Costs and Trade-offs

Microservices are not automatically better. They introduce network failures, multiple deployments, service authentication, API versioning, queues, distributed logging, eventual consistency, more difficult debugging, and increased operational cost.

If the project has one developer, low traffic, and one server, immediate separation may increase complexity without delivering enough benefit.

10. Recommended Adoption Path

  1. Separate UI from business logic: keep one repository but define clean OSINT and Dynamic service interfaces.
  2. Add API and job boundaries: introduce FastAPI, request/response schemas, durable queues, and explicit job states.
  3. Separate the Dynamic service first: browser execution has the clearest scaling and security-isolation requirements.
  4. Separate the OSINT service when needed: do this when independent scaling, external API use, or independent deployment becomes valuable.
Recommendation. Prepare both capabilities as independently testable services, but split their deployments gradually. The strongest initial microservice boundary is the Dynamic Playwright service because it has substantially different resource and security requirements from passive OSINT.
