Web Investigation Framework Proposal

Current code assessment and a design for a reusable, pipeline-based framework

Executive summary. The current project is a Streamlit-based modular monolith containing two major capabilities: OSINT and Dynamic Web Investigation. It already has useful modules and some framework-like abstractions, particularly in the OSINT collectors. The recommended next step is to create a UI-independent, pipeline-based investigation framework with stable models, stage contracts, repository interfaces, and plugin registries. FastAPI microservices can then wrap this framework without placing business logic in API routes.

1. Current Form of the Code

The project is currently organized as one application with modular features:

Web Investigator application
|
|-- Streamlit presentation layer
|-- Dynamic web investigation module
|-- OSINT investigation module
|-- Database and storage code
|-- Reporting code
`-- Tests

This is best described as a modular monolith. Its capabilities are logically separated in Python modules, but they execute in the same application and are invoked through direct imports.

1.1 Application entry point

app.py is the main Streamlit application. It creates the UI, manages session state, selects workspaces, validates targets, creates investigation IDs, starts Playwright investigations, and displays results. Consequently, presentation and workflow coordination are currently coupled.

1.2 Dynamic Web Investigation component

core/
|-- browser_engine.py
|-- playwright_session.py
|-- nav_engine.py
|-- validator.py
|-- keyword_detector.py
|-- payment_detector.py
`-- image_annotator.py

These modules cooperate as one feature. The component is not yet an independent service or reusable framework module because it uses concrete browser, database, configuration, and callback implementations.

1.3 OSINT component

osint/
|-- collectors/
|-- orchestrator.py
|-- models.py
|-- normalizer.py
|-- resolver.py
|-- risk.py
|-- storage.py
|-- evidence_capture.py
`-- report modules

The OSINT component is closer to a reusable framework because it already has a collector base class, collector context, collector registry, standardized collector results, an orchestrator, data models, a repository layer, and report builders.

1.4 UI, persistence, and tests

The ui/ directory contains Streamlit presentation logic, although some workflow decisions remain in UI code. Persistence is split between database/db_manager.py and osint/storage.py, with different interfaces and schemas. The tests currently provide strong groundwork around OSINT target resolution, foundations, and domain intelligence, but a framework will also need pipeline, plugin-contract, Dynamic engine, storage-adapter, retry, and failure tests.

2. Application Versus Framework

An application directly executes a particular workflow:

engine = PlaywrightInvestigationEngine(...)
engine.run_investigation(...)

A framework defines stable contracts so that implementations can be inserted or replaced:

pipeline.register_stage(OSINTDiscoveryStage())
pipeline.register_stage(DynamicBrowserStage())
pipeline.register_stage(CustomMalwareScanStage())

A framework should define how investigations, stages, results, errors, progress, retries, cancellation, evidence, storage, extensions, and reports are represented.

3. Recommended Framework Concept

The proposed Web Investigation Framework should accept a target, execute configured stages, correlate evidence, assess risk, and produce unified results. It must not depend directly on Streamlit or FastAPI.

                         Streamlit UI
                              |
                         FastAPI APIs
                              |
                              v
                  Web Investigation Framework
                              |
            +-----------------+-----------------+
            |                 |                 |
            v                 v                 v
        OSINT module    Dynamic module     Future modules

The same framework can then be used by Streamlit, FastAPI, a CLI, workers, scheduled jobs, and automated tests.

5. Central Framework Concepts

5.1 Investigation case

One object should represent the complete case:

@dataclass
class InvestigationCase:
    case_id: str
    original_target: str
    status: str
    created_at: datetime
    selected_modules: list[str]
    target_ids: list[str]
CASE_2026_000123
|-- OSINT run
|-- Dynamic run for example.com
|-- Dynamic run for payments.example.com
|-- Correlated evidence
`-- Final report

5.2 Investigation context

Every stage receives a common context that carries results forward:

@dataclass
class InvestigationContext:
    case: InvestigationCase
    targets: list[Target]
    observations: list[Observation]
    evidence: list[Evidence]
    findings: list[Finding]
    metadata: dict

5.3 Standard pipeline stage

class InvestigationStage(ABC):
    name: str

    @abstractmethod
    def execute(
        self,
        context: InvestigationContext,
    ) -> StageResult:
        pass

Possible stages include Target Validation, Target Resolution, OSINT Collection, Candidate Selection, Dynamic Crawl, Keyword Detection, Payment Detection, Evidence Correlation, Risk Assessment, and Report Generation.

5.4 Standard result and status

@dataclass
class StageResult:
    stage_name: str
    status: str
    observations: list[Observation]
    evidence: list[Evidence]
    errors: list[StageError]
    started_at: datetime
    completed_at: datetime

Recommended statuses:

PENDING
QUEUED
RUNNING
WAITING_FOR_INPUT
COMPLETED
PARTIAL
FAILED
CANCELLED
SKIPPED

WAITING_FOR_INPUT is especially useful for target approval and manual browser authentication.

5.5 Pipeline execution

pipeline = InvestigationPipeline(
    stages=[
        ValidateTargetStage(),
        ResolveTargetStage(),
        OSINTCollectionStage(),
        CandidateSelectionStage(),
        DynamicCrawlStage(),
        EvidenceCorrelationStage(),
        RiskAssessmentStage(),
        ReportGenerationStage(),
    ]
)

result = pipeline.run(case)

The pipeline should support optional stages, dependencies, retries, timeouts, cancellation, progress events, resumability, and manual approval points.

6. Plugin and Extension Model

A framework should allow new capabilities to be registered without modifying the core engine.

6.1 Collectors

class DNSCollector(Collector):
    name = "dns"

    def collect(self, target, context):
        ...

registry.register_collector(ThreatFeedCollector())

Potential collectors include DNS, RDAP, search, Wayback, browser, and document collectors.

6.2 Detectors

class Detector:
    name: str

    def detect(self, page: PageArtifact) -> list[Finding]:
        ...

Implementations could include Keyword, Payment, Gaming, Authentication, QR Code, Malware Indicator, and Crypto Wallet detectors.

6.3 Correlators and reporters

Correlators can connect domain, identity, payment, and infrastructure evidence. Reporter plugins can generate JSON, CSV, HTML, DOCX, or PDF output.

7. Configuration-Driven Pipelines

Pipeline definitions should be configuration-driven instead of hardcoded:

pipelines:
  complete_investigation:
    stages:
      - target_validation
      - target_resolution
      - osint_collection
      - analyst_target_selection
      - dynamic_investigation
      - evidence_correlation
      - risk_assessment
      - report_generation

  passive_osint:
    stages:
      - target_validation
      - target_resolution
      - osint_collection
      - risk_assessment
      - report_generation

  dynamic_only:
    stages:
      - target_validation
      - dynamic_investigation
      - risk_assessment
      - report_generation

The UI can present these definitions as investigation modes while the framework decides which stages execute.

8. Framework and Microservices

The framework should be built before microservice deployment:

Framework
|-- Contracts and models
|-- Pipeline engine
|-- OSINT stages
|-- Dynamic stages
`-- Reporting

Microservices then become thin deployment wrappers:

OSINT FastAPI service
    `-- imports OSINT framework modules

Dynamic FastAPI service
    `-- imports Dynamic framework modules

Pipeline FastAPI service
    `-- imports pipeline framework modules

Business logic should not be embedded inside FastAPI routes. Routes should validate requests, call application services, and return responses.

9. Framework Boundaries

The core framework should not know about Streamlit widgets, HTTP request objects, FastAPI responses, CSS, UI session state, database connection details, or deployment mechanisms.

UI / API layer
      |
      v
Application service layer
      |
      v
Framework and domain layer
      |
      v
Infrastructure adapters

This separation keeps the investigation logic reusable and independently testable.

10. Repository Strategy

A separate Git repository is not required initially. A modular monorepo is recommended while contracts are evolving:

One Git repository
|-- Framework package
|-- OSINT service
|-- Dynamic service
|-- Streamlit UI
`-- Tests

Separate repositories become useful when different teams own services, release schedules differ, access permissions differ, and framework contracts have stabilized.

11. Recommended Development Sequence

  1. Define framework contracts: create InvestigationCase, InvestigationContext, InvestigationStage, StageResult, Observation, Evidence, repository interfaces, and the pipeline status model. Preserve existing behavior.
  2. Adapt existing modules: wrap the OSINT orchestrator as an OSINT stage, the Playwright engine as a Dynamic stage, the risk scorer as a Risk stage, and report builders as Reporter plugins.
  3. Add the unified pipeline: connect stages using a common case ID and shared context. Add pause points for candidate approval, browser login, and analyst review.
  4. Separate the UI: make Streamlit call application services rather than directly constructing repositories and engines.
  5. Add FastAPI: expose OSINT, Dynamic, and Pipeline APIs using thin endpoint layers.
  6. Add production infrastructure: introduce PostgreSQL, Redis or RabbitMQ, workers, object storage, authentication, monitoring, and container isolation.

    |-- Streamlit UI
    |-- FastAPI services
    |-- Background workers
    `-- CLI
Final recommendation. Create a modular, pipeline-based investigation framework first. Preserve the working OSINT and Dynamic implementations and place adapters around them. Once the contracts and pipeline boundaries are stable, expose the components as FastAPI microservices. This provides reuse and extensibility without prematurely rewriting working investigation logic.

Prepared for the Web Investigator project. This document is an architectural proposal; the framework structure and service boundaries described here have not yet been implemented.
